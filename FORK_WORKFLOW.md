# Как вести форк Multica

Держите `origin/main` зеркалом `upstream/main`, а свои доработки объединяйте в
`origin/fork/main`. Тогда `main` можно обновлять без конфликтов, а совместимость
с доработками проверять отдельно, до публикации новой версии форка.

| Ветка | Назначение |
| --- | --- |
| `main` в `origin` (`Mexanik72/multica`) | Зеркало `main` из `upstream` (`multica-ai/multica`). Только fast-forward, без собственных коммитов. |
| `fork/main` в `origin` | Основная ветка форка. База для обычных PR и собственных сборок. Историю не переписываем. |
| `agent/<задача>` | Одна доработка; создавайте от свежей `origin/fork/main`. |
| `sync/<дата-или-версия>` | Временная ветка от `origin/fork/main` для обновления из `upstream/main`. |

## Начните работу в форке

1. Обновите зеркало по инструкции ниже. Если `fork/main` ещё нет, создайте её
   один раз из свежей `origin/main` и опубликуйте в `origin`:

   ```bash
   git switch --create fork/main --no-track origin/main &&
     git push --set-upstream --no-follow-tags origin fork/main
   ```

2. Для каждой доработки заведите отдельную ветку:

   ```bash
   git fetch --no-tags origin &&
     git switch --create agent/my-change --no-track origin/fork/main
   ```

3. Открывайте PR с базой `Mexanik72/multica:fork/main`. Обычный PR можно
   объединить через squash, если итоговый коммит описывает одну законченную
   доработку. Синхронизацию upstream объединяйте с сохранением истории.

Если форк станет основным местом разработки, назначьте `fork/main` веткой по
умолчанию и запретите force push в обе долгоживущие ветки. При настройке правил
для `main` оставьте возможность обновлять её fast-forward. Текущие workflow
[CI](.github/workflows/ci.yml) и [Mobile Verify](.github/workflows/mobile-verify.yml)
нацелены на `main`. До настройки сборки для `fork/main` запускайте проверки по
разделу Development and Verification в [AGENTS.md](AGENTS.md) локально.

## Ограничивайте расхождение с upstream

- Настройки окружения и развёртывания держите вне общего кода, когда это
  позволяет существующая конфигурация. Изменения только для форка размещайте
  в отдельных модулях или конфигурации, если есть подходящая точка расширения.
- Делайте отдельный PR на каждую задачу. В описании фиксируйте, зачем она
  нужна, какие общие компоненты затрагивает и можно ли перенести её в upstream.
  Придерживайтесь [требований к PR](CONTRIBUTING.md#pull-request-requirements).
- Исправления, полезные всем, по возможности отправляйте в upstream. Для
  upstream PR создайте отдельную ветку от свежей `upstream/main` и перенесите
  только нужные коммиты через `cherry-pick`. Если upstream уже решает ту же
  задачу, при следующем обновлении проверьте, можно ли убрать код форка.
- Избегайте массового форматирования, переименований и побочных рефакторингов
  в доработках форка. Они увеличивают число мест, которые придётся проверять
  при каждом обновлении.

## Обновляйте форк

Проверяйте upstream раз в неделю и перед выпуском форка. Если готовится
критичное исправление в одной из ваших зависимостей от upstream, обновляйтесь
после его выхода. Начинайте с чистого рабочего дерева.

1. Обновите зеркало. Проверка `rev-parse` не даст отправить локальные коммиты,
   если кто-то случайно добавил их в `main`. При отказе Git разберитесь в
   расхождении веток, прежде чем продолжать.

   ```bash
   git fetch --no-tags origin &&
     git fetch --no-tags upstream &&
     git switch main &&
     git merge --ff-only upstream/main &&
     test "$(git rev-parse HEAD)" = "$(git rev-parse upstream/main)" &&
     git push --no-follow-tags origin main
   ```

2. Если `git log --oneline origin/fork/main..upstream/main` показывает новые
   коммиты, создайте ветку синхронизации и влейте upstream. Подставьте дату
   обновления вместо даты в примере. Для первого запуска, когда `fork/main`
   ещё нет, достаточно предыдущего шага.

   ```bash
   git switch --create sync/2026-11-14 --no-track origin/fork/main &&
     git merge --no-ff upstream/main
   ```

3. Разрешите конфликты с учётом обеих сторон. Если решение неясно, выполните
   `git merge --abort`; стабильная ветка форка останется на прежнем коммите.
   После разрешения конфликтов завершите merge и просмотрите `git diff
   upstream/main HEAD`: после обновления эта команда показывает оставшиеся
   отличия форка. Прогоните проверки затронутых частей из [AGENTS.md](AGENTS.md),
   а при широких изменениях веба и сервера — `make check`. Проверьте вручную
   ключевые сценарии, которые добавляет форк.

4. Опубликуйте ветку и откройте PR в `Mexanik72/multica:fork/main`. Укажите
   SHA старой и новой базы upstream, решения по конфликтам и результаты
   проверок. Выберите **Create a merge commit**, чтобы Git сохранил связь с
   upstream. Если вливаете локально, используйте fast-forward из проверенной
   ветки синхронизации; если `fork/main` успела продвинуться, сначала обновите
   ветку синхронизации и перепроверьте результат. После вливания убедитесь,
   что `git merge-base --is-ancestor upstream/main origin/fork/main` возвращает
   код `0` после `git fetch --no-tags origin` (проверяйте тот SHA upstream,
   который вливали, если локальная ссылка уже обновилась).

## CI для Docker

Для полного self-hosted Multica собираем два образа из одного коммита.
Существующий [Dockerfile](Dockerfile) собирает backend, а
[Dockerfile.web](Dockerfile.web) — веб-интерфейс. Оба запускаются через
[штатный Compose-файл](docker-compose.selfhost.yml), который также скачивает
готовый образ PostgreSQL с pgvector.

Workflow [Fork Docker](.github/workflows/fork-docker.yml) запускается при
push в `fork/main` в `Mexanik72/multica`. Он собирает обе версии для
`linux/amd64` и после проверки публикует их в GHCR с общим тегом
`sha-<полный SHA коммита>`. Для сервера `aarch64` добавьте сборку
`linux/arm64` в workflow. Перед слиянием PR запускайте проверки затронутых
частей по [AGENTS.md](AGENTS.md).

Для проверки CI ждёт ответа `200` от backend `GET /readyz`. Этот endpoint
проверяет подключение к БД и наличие применённых миграций. Затем CI открывает
веб-страницу и проверяет `GET /health` через веб-порт, чтобы проверить
соединение веба с backend. Если за отведённое время сервисы не отвечают, job
завершается с ошибкой и выводит логи Compose. Как работает проверка готовности
и проксирование, видно в [health.go](server/cmd/server/health.go) и
[proxy.test.ts](apps/web/proxy.test.ts).

Публикация использует `GITHUB_TOKEN` с `packages: write`. В отчёте успешного
запуска указаны полные имена обоих образов с тегами. Для развёртывания
используйте общий тег из этого отчёта.
При первом выпуске GHCR создаёт приватные пакеты. Для их скачивания серверу
нужен токен с `read:packages`. [Документация GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#authenticating-to-the-container-registry)

После первой публикации задайте в `.env` на сервере:

```dotenv
MULTICA_BACKEND_IMAGE=ghcr.io/mexanik72/multica-backend
MULTICA_WEB_IMAGE=ghcr.io/mexanik72/multica-web
MULTICA_IMAGE_TAG=sha-<полный SHA из успешной сборки>
```

Обновляйте оба сервиса одним `docker compose -f docker-compose.selfhost.yml
pull`, затем применяйте оба образа через `docker compose -f
docker-compose.selfhost.yml up -d`. Успешная сборка даёт версию для
развёртывания, которое запускает оператор. При откате версии после миграций
сначала проверьте совместимость предыдущего backend с текущей схемой БД.

## Миграции и релизы

- **Миграции.** По возможности добавляйте общие изменения схемы через upstream.
  Для миграций форка перед выпуском проверьте, что их номера не пересекаются с
  upstream. Номера можно менять только до применения в постоянных базах.
  Если номер уже применён и совпал с новой миграцией upstream, не меняйте
  применённые файлы и `schema_migrations` вручную. Сначала подготовьте и
  проверьте путь обновления на копии базы. Для изменений SQL следуйте
  требованиям [AGENTS.md](AGENTS.md#database-and-migration-rules), включая
  `make sqlc` при изменении SQL для sqlc.
- **Релизы.** Для первого варианта достаточно Docker-образов с тегом коммита.
  Если понадобятся именованные релизы, используйте отдельный префикс Git-тегов
  форка, например `fork-v`. Теги `v*.*.*` запускают унаследованный
  [Release workflow](.github/workflows/release.yml).
